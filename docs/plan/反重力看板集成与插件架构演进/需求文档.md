## 1. 需求背景与目标概述

### 1.1 业务背景
目前开发者个人维护两个面向 Antigravity 桌面客户端的插件仓库：
1. **`antigravity-skin`（换肤插件）**：提供动态视频/Web/Scene 壁纸、毛玻璃穿透、开机引导动画、隔离中文汉化、官方设置菜单集成与在线热更新能力；
2. **`antigrative-dashboard`（反重力看板，插件 ID 为 `antigravity-pulse`）**：提供模型选择旁内嵌监控条（生成速率 tok/s、缓存命中率、上下文占用）、5 小时 / 周额度共享详情、历史对话统计持久化、本地 Token 用量统计图表以及官方辅助侧边栏（Aux Pane）常驻面板。

两个插件均依赖 Antigravity 的 `~/.gemini/config/plugins/` 规范及 Sidecar + CDP 注入机制运行，用户目前需要分别前往两个仓库下载、安装与维护，存在以下痛点：
1. **安装与升级割裂**：用户需要安装两次插件、维护两套脚本，版本协同与热更新成本高；
2. **存量冲突与迁移成本**：部分用户已单独安装 `antigrative-dashboard`（`antigravity-pulse`），直接集成后若不妥善替换，会出现两个实例争抢 DOM 挂载、重复绑定 CDP、覆盖写入设置或历史用量数据断层的问题；
3. **缺少可视化统一开关**：看板目前仅支持命令行 `manage.py enable/disable` 或直接改写全局配置，缺少在 Antigravity 客户端界面内的直观开关；
4. **每次客户端更新都要重新注入（核心痛点）**：自 Antigravity v2.33.0+ 默认关闭 CDP 调试端口（且删除 `DevToolsActivePort`）并整体替换 `resources/app.asar` 后，每次官方自动更新都会导致客户端补丁丢失，用户不得不重新执行安装脚本，且“客户端内一键修复”也因无 CDP 而无法加载。

### 1.2 核心目标
1. **一仓一体集成**：将 `antigrative-dashboard` 的桌面端核心能力完整集成至 `antigravity-skin`，用户只需安装 `antigravity-skin` 即可同时获得换肤与看板能力；
2. **平滑替换存量看板**：安装新版集成插件时，自动识别、无损迁移历史数据并安全替换/卸载原有的独立版 `antigravity-pulse` 插件；
3. **原生设置开关集成**：在 Antigravity 设置弹窗的 **「模型与用量（Models & Usage）」** 标签页下、**「套餐详情（Your Plan / Plan）」** 下方，注入看板开关与快捷控制区；
4. **插件形态演进与免手动重注调研**：系统性调研 Antigravity 官方扩展机制与现有注入机制的技术边界，给出“减少/消除每次更新后手动重注”的落地解法及插件长期演进路线。

## 2. 需求一：反重力看板一体集成方案

### 2.1 功能集成范围界定

| 源仓库模块 | 集成策略 | 说明 |
| :--- | :--- | :--- |
| **桌面端内嵌监控条**（`compat/inline-widget.cjs`、`usage-ui.cjs`、`i18n.cjs`、`theme.cjs`、`runtime-ui.mjs`） | **完整集成** | 保留 Shadow DOM 隔离、主对话与子代理（Teamwork）独立统计、窄窗口三图标降级、Hover/Click 详情卡与 Token 用量统计弹窗。 |
| **桌面端数据采集与 Aux Pane 面板**（`sidecars/panel/*`） | **完整集成** | 保留 `MetricsStore`、`DesktopUsage`、V4 桥接协议、`SidecarOwner` 所有权锁与 `SIDECAR_UI_ENTRYPOINT_AUX_PANE` 侧边栏常驻面板。 |
| **独立 `cli/`（Antigravity CLI 状态栏）** | **暂不自动安装（可按需保留/外链）** | 原 `antigrative-dashboard` 仓库后续转为仅修复关键 Bug 的维护态并逐步弃用；桌面端能力全量迁入本仓库，`cli/` 与 `ide/`（VSIX）不在桌面插件默认安装范围内，可按需保留独立使用说明。 |
| **独立 `ide/`（Antigravity IDE VSIX）** | **不在本插件默认安装范围** | Antigravity IDE 为独立的 VS Code 衍生端，使用 `.vsix` 扩展包，与桌面 App 插件目录不互通；原仓库可仅作存量 Bug 维护或归档声明。 |

### 2.2 架构融合方案对比与选型

Antigravity 插件规范天然支持在单个插件目录下声明多个 `sidecars/<name>/sidecar.json`（配置注册形如 `sidecars["<plugin>/<sidecar>"]`）。围绕 `skin-engine` 与看板 `panel` 的组织方式，评估两种方案：

| 维度 | 方案 1：单插件双 Sidecar 协同（推荐） | 方案 2：单 Sidecar 进程完全合并 |
| :--- | :--- | :--- |
| **目录结构** | `antigravity-skin/sidecars/skin-engine/` + `antigravity-skin/sidecars/dashboard/`（或 `panel/`） | 所有采集/流媒体/WebUI 合并进 `sidecars/skin-engine/main.mjs` |
| **故障隔离** | **高**：视频流/WebWallGL/壁纸渲染与 Token 统计采集进程互不拖垮 | **低**：任一模块未捕获异常或重启会影响另一模块 |
| **Aux Pane 支持** | **原生保留**：`panel` 保留 `has_web_ui: true` 与 `sidecar_sdk`，无需改造 `skin-engine` | 需让 `skin-engine` 额外承载 `sidecar_sdk` 与页面路由 |
| **代码侵入与回归风险** | **极低**：保留 `antigrative-dashboard` 的采集、计量、所有权与 80+ 单测基线 | **高**：需要重写大量路由、CDP 绑定与构建脚本 |
| **开关联动方式** | 共享读取 `antigravity-skin/config/config.json`（及实时通知接口），`RuntimeUi` 轮询或接收通知即时 `attach/detach` | 同进程内存直接控制 |

> **推荐选型**：采用 **方案 1（单插件双 Sidecar 协同）**。  
> - `sidecars/skin-engine`：继续负责换肤、动态壁纸流媒体、开屏动画、设置面板注入（含「外观」与「模型与用量」开关）、热更新及自愈探针；  
> - `sidecars/panel`（沿用目录名 `panel` 可最大限度复用原路径约定）：负责指标采集、`Aux Pane` Web UI 及通过 `RuntimeUi` 挂载输入框旁看板控件。

### 2.3 配置结构统一与向后兼容

在 `antigravity-skin/config.default.json` 及 `normalizeConfig()` 中新增 `features.dashboard` 配置节点：

```json
{
  "enabled": true,
  "features": {
    "dashboard": {
      "enabled": true,
      "inlineEnabled": true
    }
  }
}
```

**字段语义说明**：
- `features.dashboard.enabled`（boolean，默认 `true`）：反重力看板总开关。关闭后停止向渲染层挂载内嵌监控条（已挂载的立即调用卸载/清理），但保留历史持久化数据；
- `features.dashboard.inlineEnabled`（boolean，默认 `true`）：是否在模型选择器旁挂载内嵌缩略条（关闭时可仅保留 `Aux Pane` 侧边栏面板）；
- **语言联动（已确认）**：看板不再维护独立语言配置项，**统一跟随换肤插件全局语言（`features.language` / 宿主汉化状态）自动切换中英文**。原看板悬浮卡与侧面板中自带的 `English / 简体中文` 切换按钮及首次语言引导提示一并移除精简。

### 2.4 历史统计数据与用户偏好无损继承/迁移

独立版 `antigrative-dashboard`（`antigravity-pulse`）将用户数据持久化在以下位置（一旦集成后，`ANTIGRAVITY_EXECUTABLE_DATA_DIR` 默认会变为 `~/.gemini/antigravity/sidecar_data/antigravity-skin/panel/data/`）：
- 统计账本：`~/.gemini/antigravity/sidecar_data/antigravity-pulse/panel/data/history-v1/` 与 `usage-v1/`
- 语言与引导状态：
  - macOS：`~/Library/Application Support/AntigravityPulse/preferences.json`
  - Windows：`%LOCALAPPDATA%/AntigravityPulse/preferences.json`
  - Linux：`${XDG_DATA_HOME:-~/.local/share}/AntigravityPulse/preferences.json`

**FR-1.1 数据迁移与兼容规则**：
1. 安装或首次启动 `sidecars/panel` 时，若新数据目录（`sidecar_data/antigravity-skin/panel/data/`）尚无 `history-v1` / `usage-v1`，且旧目录（`sidecar_data/antigravity-pulse/panel/data/`）存在数据，应**自动复制迁移**（保留原旧目录作为冷备份，不破坏性移动）；
2. `PreferencesStore` 仅保留 `usageGuideDismissed` 等非语言偏好（或同步收口至 `antigravity-skin` 配置），**移除原看板自带的中英文切换按钮与首次语言选择引导（`languageGuideDismissed`）**，避免与换肤插件的「界面语言」产生双重开关冲突；
3. 在线热更新（`skin-engine` `/api/update/apply`）与插件重装时，白名单保护策略必须同时保护 `config/config.json`、素材目录与看板持久化数据目录，绝不覆盖清零。

### 2.5 视觉与运行时协同

1. **主题与毛玻璃自适应**：`antigrative-dashboard` 的 `inline-widget.cjs` 已经通过宿主 CSS 变量（`--primary`、`--background`、`--popover`、`--foreground`）及原生 `popover` 顶层渲染做过适配。集成后需验证：
   - 当 `antigravity-skin` 开启**动态壁纸 + 毛玻璃模式**时，看板缩略条与悬浮详情卡（Speed / Cache / Context / Usage）在浅色壁纸与深色壁纸下的文字对比度、卡片不透明度是否清晰可读；
   - `appearance-menu.js` 的 DOM `MutationObserver` 需继续忽略 `#ag-pulse-status-bar` 及其内部变动（当前代码第 3072 行已包含该过滤，需继续保持并覆盖新增设置区块 `#agy-dashboard-settings-card`）。
2. **全局语言实时联动**：当用户在「设置 - 外观」切换「界面语言（简体中文 / English）」时，除了换肤插件自身汉化引擎即时切换外，同步下发通知至 `sidecars/panel` 与页面内 `#ag-pulse-status-bar` 及 `Aux Pane` 面板，实时刷新看板中英文文案，无需重启客户端。

## 3. 需求二：自动替换并卸载存量独立版反重力看板

当用户本机已经安装独立版 `antigrative-dashboard`（插件目录 `~/.gemini/config/plugins/antigravity-pulse/`）时，安装集成后的 `antigravity-skin` 必须做到**无感平滑替换，不留双份冲突**。

### 3.1 存量识别条件
安装脚本（`scripts/install.mjs`、`install.sh`、`install.ps1`）在部署前检测以下任一条件即视为存在存量独立版看板：
1. 目录 `~/.gemini/config/plugins/antigravity-pulse/` 存在（且 `plugin.json` 中 `name === "antigravity-pulse"`）；
2. `~/.gemini/config/config.json` 中存在 `plugins["antigravity-pulse"]` 或 `sidecars["antigravity-pulse/panel"]`。

### 3.2 替换执行时序（严格有序）

```text
[1] 检测存量 antigravity-pulse
       │
       ▼
[2] 终止活跃会话 / 清理旧版 app.asar 内联补丁（若有）
    • 若存在旧版 antigrative-dashboard v0.3 的 app.asar 补丁（标记 // AG_PULSE_INLINE_V1）：
      优先通过 AntigravityPulseBackups/<ts>/patch.json 的 SHA256 校验恢复原版 app.asar；
      ⚠️ 必须在 antigravity-skin 执行 patch-boot-overlay.mjs 之前完成，避免备份哈希错乱！
       │
       ▼
[3] 迁移历史数据与用户状态
    • 读取旧版 AntigravityPulse/settings.json（若旧版 enabled === false，可继承为初始状态或提示）
    • 复制迁移 sidecar_data/antigravity-pulse/panel/data/{history-v1, usage-v1} 至新目录
    • 保留 AntigravityPulse/preferences.json 与 AntigravityPulseBackups/ 不删除
       │
       ▼
[4] 清理旧插件运行环境与配置注册
    • 若在运行中通过 CDP 清理页面残留：执行 window.__agPulseDispose?.() 与 __agPulseRuntimeBridge?.dispose()
    • 删除 ~/.gemini/config/plugins/antigravity-pulse/（校验路径安全，非符号链接且确属 plugins/antigravity-pulse）
    • 从 ~/.gemini/config/config.json 原子移除 plugins["antigravity-pulse"] 与 sidecars["antigravity-pulse/panel"]
      （若处于宿主会话内通过 JetboxWriteState RPC，先将 antigravity-pulse 置为 enabled: false，待离线/退出时彻底删键）
       │
       ▼
[5] 部署集成版 antigravity-skin（含 sidecars/skin-engine + sidecars/panel）并启用
       │
       ▼
[6] 执行 antigravity-skin 内核/启动参数修补与重启恢复
```

### 3.3 边界与安全约束
1. **旧版补丁保护原则**：对齐 `antigrative-dashboard/manage.py` 的安全策略——若检测到 `app.asar` 含有 `// AG_PULSE_INLINE_V1` 但 `AntigravityPulseBackups` 中无匹配校验通过的原版备份，或文件已被第三方修改，应明确提示用户而非盲目覆盖损坏归档；
2. **宿主会话内执行保护**：若用户在 Antigravity 内置终端中触发安装脚本（`ANTIGRAVITY_LS_ADDRESS` 存在），不强杀主进程，先通过 RPC 禁用旧插件并删除其目录、迁移数据，提示用户 `Cmd+Q` / 完全退出重启后完成接管；
3. **脚本一致性**：`scripts/install.mjs`、`install.sh`（无 Node 回退分支）、`install.ps1`（无 Node 回退分支）三套安装路径均需实现上述替换检测，或统一收敛调用逻辑避免行为漂移；
4. **卸载对称性**：执行 `antigravity-skin` 卸载脚本时，完整卸载双 Sidecar 与 `antigravity-skin` 目录及配置，同时**保留** `history-v1`、`usage-v1`、`preferences.json` 等用户历史统计数据（除非用户显式传入 `--purge-data`）。

### 4.3 交互与数据流需求

1. **视觉风格对齐**：复用 `appearance-menu.js` 现有的 `createSwitchHtml`（高对比度立体胶囊开关）与 `agy-seg-group` 分段选择器风格，完美适配原生浅色、原生深色以及动态壁纸毛玻璃背景；
2. **即时生效（无需重启）**：
   - 用户点击「开启反重力看板」或「模型选择器旁内嵌监控条」开关时：
     1. 前端立即调用 `saveConfig()`（`POST http://127.0.0.1:<skinPort>/api/config`）将新状态原子写入 `antigravity-skin/config/config.json`；
     2. `sidecars/panel` 的 `RuntimeUi.enabled()` 读取同一份配置（并可由 `skin-engine` 通过本地 HTTP 通知或缩短检查间隔至 ≤1s 立即响应）；
     3. **从开到关**：`RuntimeUi` 立即执行 `detachAll()` 并调用页面侧 `window.__agPulseDispose?.()`，输入框旁的 `#ag-pulse-status-bar` 立即干净消失；
     4. **从关到开**：`RuntimeUi` 在下一次 tick（或即时触发）重新挂载 `inline-widget`，秒级恢复显示。
3. **运行状态实时回显**：卡片右上角读取 `panel` 写入的 `integration-state.json`（或 `/api/dashboard/status` 代理接口），展示当前状态：
   - `mounted`：🟢 `运行中（已挂载 X 个窗口）`
   - `waiting-for-composer`：🟡 `等待进入对话窗口`
   - `disabled`：⚪ `已停用`
   - `offline / error`：🔴 `未连接（附带简要排查提示）`
4. **DOM 隔离与防重入**：
   - 开关卡片使用唯一 ID（如 `#agy-dashboard-settings-card`）；
   - 从「模型与用量」切换到「外观」或其他标签页时，不误注入也不产生闪烁；`MutationObserver` 过滤 `#agy-dashboard-settings-card` 内部变更，防止触发循环重绘；
   - 与 `appearance-menu.js` 的全局开关解耦：**看板开关独立存在**，即便用户关闭了「自定义皮肤与动效增强」（保持官方原版外观），在「模型与用量」中依然可以独立开关反重力看板。

## 5. 需求四（专题调研）：注入式插件的出路与「每次更新重注」根治方案

> 针对核心问题：**“我们现在这种插件形式该何去何从？每次反重力更新，都得重新注入，真的好麻烦，有没有什么办法可以解决？”**  
> 本节基于 `antigravity-skin`、`antigrative-dashboard` 的源码实现及 Antigravity 2.0 官方扩展能力进行技术剖析与方案决策。

### 5.1 问题根因拆解：到底什么在更新后失效？

很多人误以为“整个插件都被官方更新删掉了”，但从底层机制看，插件其实分为**完全不同命运的两层**：

| 层级 | 存储/修改位置 | Antigravity 自动更新时是否被覆盖？ | 说明 |
| :--- | :--- | :--- | :--- |
| **第一层：插件本体与 Sidecar** | `~/.gemini/config/plugins/<name>/` 与 `~/.gemini/config/config.json` | **不会被覆盖** | 官方规范目录，宿主每次启动都会自动发现并拉起 `sidecars/*/sidecar.json` 进程！ |
| **第二层：CDP 端口开启与开机补丁** | 客户端程序包内 `resources/app.asar`（`dist/main.js`、`dist/loadingOverlay.js`）及快捷方式参数 | **每次更新 100% 被整体覆盖** | 自 Antigravity **v2.33.0+** 起，官方主进程默认关闭远程调试端口，且若启动参数无 `--remote-debugging-port` 会主动删除 `DevToolsActivePort` 文件。 |

**导致的连锁反应（“死锁困局”）**：
1. Antigravity 自动更新替换掉 `app.asar`（macOS 会替换整个 `/Applications/Antigravity.app`）；
2. `app.asar` 内注入的 `appendSwitch('remote-debugging-port', '0')` 消失 → 下次启动时 `DevToolsActivePort` 被宿主删除；
3. `skin-engine` 和 `panel` **其实已经在后台启动了**，但因为连不上 CDP 调试通道，无法往客户端主界面注入任何 DOM/CSS/JS；
4. 原本做在「设置 - 外观」里面的「一键修复补丁」按钮因为依赖 CDP 注入，**此时根本无法显示**，陷入“没有补丁就进不去设置修补丁”的死胡同，用户只能手动打开终端或重新运行安装脚本。

---

### 5.2 Antigravity 官方扩展机制能力盘点（能用官方替代吗？）

我们核查了 Antigravity 当前全部官方扩展接口（Plugins、Sidecars、MCP Apps、Hooks、IDE VSIX），能力边界如下：

| 官方能力 | 核心原理与呈现形式 | 能否实现「看板」？ | 能否实现「换肤/壁纸/设置注入/汉化」？ |
| :--- | :--- | :--- | :--- |
| **Sidecar Web UI**（`has_web_ui: true` + `SIDECAR_UI_ENTRYPOINT_AUX_PANE`） | 官方托管进程 + 内置 Web 服务器，在右侧辅助栏 `＋ → Extensions` 以 iframe 打开 | **✅ 可以**（独立侧面板完整可用，且更新永不失效） | **❌ 不能**（被沙箱隔离在 Aux Pane iframe 内，无法触达主窗口 DOM/CSS） |
| **MCP Apps**（`ui://` 资源 + `aux_pane` / `global` 入口） | 基于 SEP-1865 的标准交互式 HTML 应用，可内嵌对话卡片、侧边栏或左侧导航全屏页 | **✅ 可以**（且支持调用本地 MCP Tool 读取统计并持久化，官方生态原生支持度最高） | **❌ 不能**（受限于隔离 iframe 与严格 CSP，无法改造主界面样式或加载全屏透明壁纸） |
| **IDE VSIX**（VS Code 扩展） | 仅适用于独立 **Antigravity IDE** | **⚠️ 部分可以**（IDE 端内嵌条仍需 loopback CDP，原生仅支持 StatusBarItem） | **❌ 不能**（桌面端 Antigravity 2.0 不加载 VSIX，且 VS Code 扩展本身也不能安全修改 Workbench 全局毛玻璃） |
| **当前方案（Sidecar + CDP / Asar 补丁）** | 守护进程通过 `DevToolsActivePort` 向 Workbench 注入 JS/CSS；Windows/macOS 补丁开启端口与 T=0 开屏 | **✅ 完美内嵌**（模型选择器旁紧凑条 + 悬停详情） | **✅ 唯一解**（全屏视频/WebGL 壁纸、毛玻璃穿透、原生设置融合、全局汉化、开机动画） |

**核心结论**：
- 只要产品定位还包含**「主界面毛玻璃换肤、动态壁纸、原生设置页融合、全局界面汉化、模型选择器旁内嵌统计条」**，**在官方开放 Workbench Theme/UI Extension API 之前，CDP 注入式架构就是目前唯一可行的技术路线，无法被现有 MCP Apps 或 Sidecar Aux Pane 完全替代**。
- **但是**，**「需要用户每次更新后手动重跑安装脚本」这个问题，完全有办法通过工程架构解决或大幅缓解！**

---

### 5.3 针对两大核心失效场景的闭环解法

在实际使用中，插件不可用主要集中于以下两个场景，两者本质上共享同一个技术现场（**Sidecar 已随宿主启动，但 `app.asar` 未注入 / `DevToolsActivePort` 不可用**）：

| 失效场景 | 现场状态 | 现有痛点 |
| :--- | :--- | :--- |
| **场景 1：原生反重力首次安装本插件** | 若用户通过外部脚本安装时正处于宿主会话内（`IS_INSIDE_HOST=1`），或直接把插件放入 `~/.gemini/config/plugins/`，当前 `app.asar` 尚未写入 `remote-debugging-port=0` | 必须退出后手动运行或等待用户自行 `Cmd+Q` 重开；若未跑 `install.sh`，插件完全静默无任何提示 |
| **场景 2：反重力版本更新后首次打开** | 官方更新整体替换 `app.asar`，Sidecar 正常启动但连不上 CDP；主界面未加载，**「设置 - 外观」里原本的「一键修复」按钮也因无 CDP 而消失** | 用户看不到任何修复入口，只能重新找终端执行 `install.sh` / `install.ps1` |

#### 方案 A：Sidecar 哨兵 + 无 CDP 官方面板修复 + 退出静默自愈（主推方案 · 彻底告别手动 `install.sh`）
**核心洞察**：**无论在场景 1（首次装入插件）还是场景 2（更新覆盖 `app.asar` 后首次打开），只要插件在 `~/.gemini/config/plugins/` 下，宿主就一定会拉起 `sidecars/skin-engine` 与 `sidecars/panel`，且官方 `has_web_ui: true` 的辅助面板（`＋ → Extensions`）完全不依赖 CDP！**

这意味着我们不需要把修复入口死绑在“需要 CDP 才能注入的设置弹窗”里，而是可以建立**三层递进的零命令行闭环**：

1. **第一层 · Sidecar 启动即检（场景 1 & 场景 2 通用哨兵）**：
   - `skin-engine` 启动 100ms 内检测两件事：① `app.asar` 是否存在 `agy-video-boot-host` 与 `appendSwitch('remote-debugging-port'` 标记；② 本地 `DevToolsActivePort` 是否可用。
   - 若两者皆缺失（或 `app.asar` 补丁丢失），立即进入「待修复（`patch_missing`）」状态，**彻底解决“更新后没有反馈、找不到入口”的问题**。

2. **第二层 · 脱离 CDP 的客户端内「一键修复并重启」入口（替代手动 `install.sh`）**：
   - **官方 Aux Pane 修复横幅**：由于集成后的 `sidecars/panel` 本身就是拥有 `has_web_ui: true` 的官方侧面板，当检测到 `patch_missing` 时，面板顶部自动展示醒目的修复卡片：**「检测到反重力未激活插件通道（首次安装 / 版本已更新）→ 一键修复并重启」**。
   - **（可选）系统原生轻提醒**：检测到补丁丢失时弹出一次系统级轻通知/对话框（用户可勾选不再提醒），提供**「立即修复并重启」**与**「退出时自动修复」**两个按钮。
   - **点击「立即修复并重启」的执行链**：Sidecar 派生一个完全脱离父进程组的独立修复子进程（`detached: true` + `setsid` / PowerShell `Start-Process`）→ 优雅退出 `Antigravity` 与 `language_server` → 执行 `patch-boot-overlay.mjs`（含快捷方式参数修复）→ 自动重新拉起 `Antigravity` → **约 3 秒全自动恢复，全程无需打开终端或运行 `install.sh`**！

3. **第三层 · 退出后静默自动重注（零重启打扰，下一次打开直接生效）**：
   - **绝不主动重启或强杀正在使用的客户端**：只要用户没点“立即修复并重启”，Sidecar 就严格保持 `SKIP_KILL=1`、`SKIP_RELAUNCH=1`，不打断用户任何工作；
   - Sidecar 派生的独立轻量守望进程会在后台静默监听 `Antigravity` 与 `language_server` 进程退出（用户正常 `Cmd+Q` / 关闭窗口后），在 **2 秒内静默完成 `app.asar` 重注并直接退出（不自动重启客户端）**；用户下一次自己打开官方原版 `Antigravity` 时，皮肤与看板直接正常加载。
   - *(同时兼容改善场景 1 的内置终端安装：即使在 Antigravity 宿主会话内执行 `install.sh`，也直接接入上述“退出即自动激活”或提示在 `＋ → Extensions` 面板中点一下立即重启生效。)*

> ⚠️ **技术边界诚实说明**：Chromium 的渲染器 CDP 端口必须在 Electron `app.whenReady()` 前开启，无法对“已经无参启动的运行中进程”热开启；且官方更新必然替换 `app.asar`。因此**“更新后首次打开那一瞬”仍需要重启一次（立刻点修复重启，或关掉等下次打开）**，但**完全消除了“必须去终端手动执行 `install.sh`”的痛点**。  
> ⚠️ **macOS 签名兜底**：macOS 修改 `Antigravity.app/Contents/Resources/app.asar` 后，若系统完整性检查报错或权限弹窗重置，修复脚本可按需追加 `codesign --force --deep --sign -` 本地签名兜底。

---

#### 方案 B：Zero-Patch 纯净启动器代理（已排除 · 仅作评估记录）
**核心原理**：通过外部参数 `--remote-debugging-port=0` 拉起官方原版 `Antigravity.app` 可做到 0 改包。
- **排除原因**：在 macOS 上替身启动器会多出一个独立 `.app` 与 Dock 图标，破坏单一原生入口体验；而拦截重拉又会造成启动闪断，因此不采用。
- **Windows 快捷方式补充**：Windows 下可在**方案 A** 重注 `app.asar` 的同时顺便检查修复 `.lnk` 快捷方式参数，兼顾双保险。

---

#### 方案 C：架构分级与「双模优雅降级」（应对最坏情况的长期出路）
必须正视一个长期风险：**未来 Google Antigravity 极有可能像部分商业 Electron 应用一样，启用 Electron Fuses（如 `EnableEmbeddedAsarIntegrityValidation` + `OnlyLoadFromAsar`）或彻底从二进制层裁剪掉 `--remote-debugging-port` 开关。**

一旦发生这种上游封堵，所有依赖 CDP 注入与改包的插件将面临生存危机。为此，当前插件体系应确立**“分层演进”**的长期路线图：

1. **短中期（当下 ~ 半年）：保留注入红利 + 消除手工运维**
   - 落地 **「方案 A（Sidecar 哨兵 + 无 CDP Aux Pane 一键修复 + 退出静默重注）」**，彻底解决首次安装激活与更新后还原两大痛点，告别手动重跑 `install.sh`。
2. **中长期（架构解耦）：把「看板数据层与独立视图」向官方标准靠拢**
   - 将 `antigrative-dashboard` 的统计引擎（`MetricsStore` + `DesktopUsage`）与 UI 进一步抽象，**同时兼容 `Sidecar Aux Pane` 与 `MCP App` 标准协议**；
   - 这样即便未来 CDP 通道真的被官方彻底关闭：
     - **换肤层**退化为官方支持的主题色配置；
     - **反重力看板**依然可以作为 **100% 官方合规的 MCP App / Sidecar 扩展**（支持在右侧 Aux Pane 常驻、支持在左侧导航栏全屏打开、支持在对话中通过工具/卡片内联展示，**甚至可直接上架官方 Antigravity Marketplace！**），不会因为一次版本更新而全军覆没。
3. **生态沟通与替代探索**：
   - 调研通过 Antigravity 官方 `customThemeSeedsLight` / `customThemeSeedsDark`（在 `~/.gemini/config/config.json` 中已存在官方主题色种子字段）与官方反馈通道，推动官方提供原生的背景/自定义 CSS 扩展口。

### 5.4 方案对比总览与推荐决策

| 方案 | 解决痛点程度 | 是否修改 `app.asar` | 更新后用户手动操作 | 抗官方升级/封堵能力 | 建议定位 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **现状（手动跑脚本 + 仅开机自愈）** | 低 | 是 | 每次更新需重跑脚本 | 弱 | 待淘汰 |
| **方案 A：Sidecar 哨兵 + 退出静默重注 + Aux Pane 修复** | **高** | 是（退出后静默重注，不重启客户端） | **0 次（或按需主动点 1 下立即重启）** | 中（依赖 CDP 开关仍可注入） | **近期 P0 主推** |
| **方案 B：独立启动器替身 App** | 高 | 否 | 0 次（但会多出独立 Dock 图标） | 强 | **已排除（用户不偏好双图标）** |
| **方案 C：看板核心兼容 MCP App / Sidecar 官方插件上架** | 架构级转型 | **否** | **0 次（官方标准插件）** | **极强（官方标准，支持上架市场）** | **中长期演进方向** |

## 6. 需求评审最终结论（已全部确认）

1. **开关入口唯一位置**：只在 **「设置 -> 模型与用量 -> 套餐详情下方」** 放置看板开关卡片，不在「外观」中增加联动/镜像入口。
2. **中英文语言策略**：看板语言**统一跟随 `antigravity-skin` 插件全局语言切换**；集成时**移除原看板自带的中英文切换按钮与首次语言选择引导**，保持界面与配置统一。
3. **更新与首次激活自愈（双机制并行，全面覆盖）**：
   - **同时提供 Aux Pane 面板常驻修复入口 + 系统原生轻弹窗提醒**（每次补丁缺失仅提醒一次，提供「立即修复并重启」与「退出时自动修复」按钮，支持记住关闭弹窗偏好）；
   - 无论用户是否点击，后台均挂起**退出静默守望**：用户不点立即重启时绝不打断会话，待其自行退出客户端后 2 秒内静默重注 `app.asar`（不自动重启客户端），下次打开即刻恢复生效。
4. **独立 `.app` 启动器排除**：不采用产生额外 Dock 图标的独立替身 App 方案，保持用户直接启动官方原版 `Antigravity` 的唯一入口习惯。
5. **原 `antigrative-dashboard` 仓库定位**：后续主要在 `antigravity-skin` 维护演进；原仓库仅作存量 Bug 维护并逐步弃用（归档提示迁移）。

- [ ] 关闭「自定义皮肤与动效增强」总开关后，看板依然受「模型与用量」中的独立开关控制，互不干扰。

### 7.4 首次安装与更新自愈能力（按最终确认方案验收）
- [ ] **场景 1（首次安装无补丁兜底）**：若插件仅被部署到 `~/.gemini/config/plugins/antigravity-skin/` 而尚未重注 `app.asar`（或在宿主内置终端跑完安装尚未重启），打开右侧 `Aux Pane` 面板即可看到「一键激活并重启」入口（无需再去终端执行 `install.sh`）；
- [ ] **场景 2（更新覆盖后首次打开）**：模拟 Antigravity 客户端升级覆盖 `app.asar` 后启动客户端：
  - Sidecar 能在无 CDP 条件下立即识别“更新导致补丁丢失”；
  - 用户可在右侧 `Aux Pane` 面板（或系统轻提醒）点击「立即修复并重启」在 3 秒内自动恢复，**全过程无需打开终端运行 `install.sh`**；
  - 若用户暂不重启并正常关闭 Antigravity，后台守望进程在客户端彻底退出后 2 秒内静默完成 `app.asar` 重注且**不自动重启客户端**，下次打开自动恢复生效。
